## 2. Repository component contract

`ContinuityWitnessPort` is an application-facing, purpose-specific interface.
Its operations correspond one-for-one to section 3 endpoints. Inputs and
outputs are typed representations of the versioned schemas; transport status,
headers, TLS, serialization, and endpoint URLs do not leak into the core.
Mutation methods never retry automatically. Read methods may use the bounded
retry policy in section 3.3 and never create authority.

`ContinuityWitnessHttpAdapter` is the only defined HTTP translation boundary.
It validates an outgoing object against the exact request schema, serializes
JSON, performs one HTTPS exchange, rejects non-JSON or schema-invalid results,
validates the signed evidence envelope before returning evidence, and maps
transport/protocol failures to closed error classes. This definition does not
implement network calls, select authentication, ingress, DNS, TLS termination,
service discovery, an AWS account, region, or concrete host.

The External Witness JSON API owns the durable Stage A and Stage B operations.
AIControlCenter coordinates the human workflow but cannot manufacture an
approval, select a host identity or signing key, bypass preconditions, force a
transition, recover a claim, or convert evidence into Production authority.

## 3. Versioned JSON API

### 3.1 Common wire rules

All media are `application/json`. Every top-level request and response is an
object with `schema_version: "1"`; unknown fields are rejected and required
fields cannot be omitted. Identifiers are lowercase canonical UUID strings
(UUIDv7 generated by the owning service) except cryptographic key versions,
which are nonempty opaque strings. Timestamps are UTC RFC 3339 strings with
exactly microsecond precision and `Z`. Integers are JSON integers in the range
0 through 9,007,199,254,740,991. Floats, NaN, Infinity, duplicate object keys,
implicit nulls, padded base64, and alternate identifier spellings are invalid.

Binary values use strict unpadded base64url. SHA-256 and HMAC-SHA-256 values
are exactly 32 bytes. A challenge nonce is exactly 32 bytes. Enum values are
case-sensitive. Request and response bodies have endpoint-specific size limits;
any object passed to a signing adapter has a maximum RFC 8785 JCS encoding of
4096 bytes.

Stable identifiers have these owners:

| Identifier | Owner and stability |
| --- | --- |
| `request_id` (challenge request) | AIControlCenter-assigned before POST; immutable UUIDv7 idempotency and reconciliation key |
| `challenge_id` | Witness-assigned; immutable; one evaluation only |
| `nonce` | Witness-generated; exactly 32 bytes; caller can never select it |
| `evaluation_id` | AIControlCenter-assigned before POST; immutable reconciliation key |
| `approval_id` | Human approval artifact issuer; globally unique and immutable |
| `claim_id` | AIControlCenter-assigned before Stage A POST; immutable reconciliation key |
| `operation_id` | AIControlCenter-assigned before Stage B POST; immutable reconciliation key |
| `continuity_host_id` | Witness-assigned only; immutable for one physical Mac record |
| `transition_id` | Witness-assigned; immutable append identity |
| `checkpoint_id` | Witness-assigned; immutable publication identity |

Every JSON HTTP response intentionally produced by the Witness, including every
success and closed API, application, authentication, authorization, and
access-control error, contains a complete non-null `signed_evidence` envelope:

```json
{
  "schema_version": "1",
  "domain": "WITNESS_PROTOCOL_EVIDENCE",
  "evidence_type": "<endpoint-specific enum>",
  "request_id": "<stable request/evaluation/claim/operation id>",
  "issued_at": "<timestamp>",
  "witness_key_id": "<opaque purpose-bound id>",
  "witness_key_version": "<opaque version>",
  "payload_schema_version": "1",
  "payload_digest": "<base64url SHA-256 of JCS application payload>",
  "signature": "<base64url Ed25519 signature>"
}
```

The signed object passed to `WitnessSigner` excludes only `signature`; it binds
the application payload by digest rather than signing a large payload inline.
The envelope is evidence only. It grants no Production, install, bootstrap,
SEC-02, execution, release, retry, rollback, or generic authorization.

### 3.2 Error model

Non-2xx errors use:

```json
{
  "schema_version": "1",
  "error": {
    "classification": "MALFORMED|UNAUTHORIZED|FORBIDDEN|NOT_FOUND|CONFLICT|REPLAYED|UNAVAILABLE|UNCERTAIN|INTERNAL_CLOSED",
    "code": "<stable endpoint-specific code>",
    "message": "<bounded non-sensitive text>",
    "request_id": "<stable id or null>",
    "retry_disposition": "NEVER|READ_ONLY_SAME_ID_ONLY|NEW_EVALUATION_AND_NEW_APPROVAL_REQUIRED"
  },
  "signed_evidence": "<complete signed Witness evidence envelope>"
}
```

TLS failure, connection failure, timeout without a complete response, truncated
response, non-JSON response, reverse-proxy or intermediary output not
authenticated as Witness output, local outgoing schema-validation failure, and
a malformed or signature-invalid purported Witness response are adapter-local
failures, not Witness API responses. The adapter returns `UNAVAILABLE`,
`MALFORMED`, or `UNCERTAIN` as appropriate. Such a result has no Witness
`signed_evidence` and grants zero authority.

`MALFORMED` includes schema, encoding, canonicalization, attestation, and
signature structure failures. `UNAUTHORIZED`/`FORBIDDEN` concern API access
only and confer no lifecycle authority. `CONFLICT` means the stable identifier
already binds different canonical input. `REPLAYED` means single-use evidence
was presented again. `UNAVAILABLE` is a definite dependency inability with no
positive result. `UNCERTAIN` means the exact durable outcome cannot be proven.
Errors never include raw UDID, raw serial, nonce, approval signature, key
material, credentials, attestation body, or authority-bearing artifacts.

### 3.3 Idempotency, replay, and retry

For each POST the named stable identifier is the idempotency key and is also
sent in `Idempotency-Key`. A repeated byte-equivalent canonical request may
return the exact stored result only where the endpoint below permits it; the
header/body mismatch or same ID with different canonical input is `CONFLICT`.
Returning a stored result is read-only reconciliation, not re-execution.

No mutation POST is automatically retried after timeout, disconnect, 5xx,
ambiguous COMMIT acknowledgement, or ambiguous checkpoint publication. Only
the corresponding GET with the exact stable ID may reconcile it. GET may be
retried with bounded exponential backoff (maximum three attempts, full jitter,
respecting `Retry-After`) only for transport timeout, 408, 429, 502, 503, or
504. Do not retry malformed, unauthorized, forbidden, not-found, conflict,
replayed, signature-invalid, key-ambiguous, or history-conflicting results.

Challenges and approval artifacts are single-use. A replay never creates a
new evaluation, claim, operation, or authority. A new lifecycle attempt after
a definitive or uncertain consumed outcome requires a new challenge (when MDA
is required), new evaluation, new approval, new claim, and new operation.

The corresponding operation constraints are:

- GENESIS has cardinality 1 and role `TARGET`; it requires complete verified
  historical absence and fresh MDA, Witness assignment of a new host ID,
  enrollment generation 1, final state `ACTIVE`, and nondecreasing maxima.
- RECOVERY has cardinality 1 and role `TARGET`; it requires fresh MDA,
  preservation of the existing host identity and enrollment generation, final
  state `ACTIVE`, and nondecreasing maxima.
- DECOMMISSION has cardinality 1 and role `TARGET`; it requires no fresh MDA,
  the exact current evaluation, host, and record generation, terminal final
  state `DECOMMISSIONED`, and nondecreasing maxima.
- MIGRATION has cardinality 2 and ordered roles `PREDECESSOR`, `SUCCESSOR`; it
  requires fresh successor MDA, predecessor final state `DECOMMISSIONED`,
  Witness assignment of a distinct new successor host ID, successor enrollment
  generation 1 and final state `ACTIVE`, successor lineage bound to the
  predecessor, and nondecreasing maxima. It remains one effective operation.

DECOMMISSION and otherwise null. `expected_predecessor_continuity_host_id` is
set only for MIGRATION. `expected_record_generation` is the current generation
for RECOVERY, DECOMMISSION, and MIGRATION and null for GENESIS.
`validated_hardware_evidence_binding_digest` is the exact validated fresh
hardware/evidence binding digest for GENESIS, RECOVERY, and MIGRATION and null
for DECOMMISSION. `TransitionIntent` contains no Stage-B-generated
`transition_id`, GENESIS host ID, MIGRATION successor host ID,
`resulting_transition_digest`, `resulting_transition_digests`, or checkpoint
object digest.

Stage-B-generated value. Human approval and `LifecycleApprovalVerifier` bind
and verify exactly `expected_transition_intent_digest`. Stage A durably claims
the approval bound to that digest. Stage B re-derives and revalidates the exact
`TransitionIntent` before mutation, then emits ordered
`resulting_transition_digests` as output evidence only.

## 4. PostgreSQL logical schema and transaction model

### 4.1 Required entities and invariants

The replaceable store is PostgreSQL-compatible. Schema migrations are future
implementation work. Logical entities are:

| Entity | Required content and constraints |
| --- | --- |
| `continuity_hosts` | PK host ID; immutable enrollment generation and predecessor lineage; lifecycle state; nondecreasing version maxima; record generation; latest transition digest; optional current/latest hardware-binding convenience metadata; timestamps; no hard delete; not historical hardware-binding authority |
| `continuity_hardware_bindings` | PK binding ID; host ID; hardware-binding index/key ID/key version; source evaluation ID; created time; append only; exact key-version/index tuple binds at most one host and duplicate or multiple-host matches conflict |
| `continuity_transitions` | PK transition ID; operation/host IDs; type; from/to state; previous/resulting digest; generation; canonical transition payload digest; created time; append only |
| `identity_evaluations` | PK evaluation ID; operation; challenge/evidence/index digests; classification; history coverage; relevant host/generation/digest; expiry; immutable result |
| `lifecycle_approval_claims` | PK claim ID; unique approval ID; unique operation ID; evaluation/type/expected-host and exact transition-intent-digest bindings; approval digest/key identity; state; claim/terminal times; no delete/reuse |
| `lifecycle_operations` | PK operation ID; unique claim ID; evaluation/type bindings; durable status; exact source/result facts; checkpoint publication state; immutable canonical request digest |
| `witness_challenges` | PK challenge ID; unique AIControlCenter-owned request ID; evaluation ID; operation; nonce digest and protected Witness-generated nonce; issue/expiry/consumed times; single use |
| `audit_events` | PK event ID; transaction ID; entity IDs; classification; source/result digests; signing key identity; created time; append only |
| `immutable_checkpoint_publications` | PK checkpoint ID; unique operation and sequence/generation; DB transaction identity; object key; opaque immutable version ID when established; object digest; previous checkpoint digest; publication/verification state; append only |

Foreign keys bind every claim to one evaluation and operation, every operation
to one claim/evaluation, every transition and checkpoint to one operation, and
every relevant row to audit events. Unique constraints prevent a challenge,
approval, claim, or operation from being rebound. Raw UDID, serial, attestation,
approval signature, and reusable nonce are not general audit fields.

The append-only `continuity_hardware_bindings` relation has at minimum
`binding_id`, `continuity_host_id`, `hardware_binding_index`,
`hardware_binding_key_id`, `hardware_binding_key_version`,
`source_evaluation_id`, and `created_at`. A unique constraint on
(`hardware_binding_key_id`, `hardware_binding_key_version`,
`hardware_binding_index`) prevents one key-version/index from binding multiple
continuity identities. A second unique constraint on (`continuity_host_id`,
`hardware_binding_key_id`, `hardware_binding_key_version`,
`hardware_binding_index`) rejects duplicate rows for one identity. Conflicting
insert or lookup results fail closed rather than selecting a winner.

Lifecycle and claim state changes use explicit compare-and-set predicates and
row locks. Isolation is `SERIALIZABLE` with constraint enforcement; serialization
failure is a failed attempt, not retry authority. No automatic transaction
retry exists.

### 4.2 Stage A: durable claim transaction

Before `BEGIN`, parse and verify the approval through
`LifecycleApprovalVerifier`, validate the immutable evaluation result, exact
operation/evaluation/type/host/transition-intent-digest binding, key purpose and
validity, freshness/expiry, and absence of prior use. Then:

1. `BEGIN ISOLATION LEVEL SERIALIZABLE` and acquire the approval identity,
   evaluation, and operation uniqueness locks.
2. Re-read the evaluation and all bindings; require its immutable digest to
   equal the verified approval payload binding.
3. Require logical approval state `AVAILABLE`, represented by absence of any
   claim for the globally unique `approval_id`; conflicting prior presence is
   replay and stops.
4. Insert the `lifecycle_approval_claims` row directly as
   `DURABLY_CLAIMED`, binding claim, approval, evaluation, operation, type,
   expected hosts, transition-intent digest, approval digest, and approval key
   ID/version.
5. Append the Stage A `audit_events` row in the same transaction.
6. `COMMIT` once. Only acknowledged commit yields a newly returned durable
   claim. Ambiguous acknowledgement yields `UNCERTAIN`; Stage B does not run.

Definitive Stage A failure before durable COMMIT creates no `DURABLY_CLAIMED`
state and therefore does not establish permanent consumption. A SERIALIZABLE
abort before durable COMMIT likewise creates no durable claim. Neither creates
automatic retry authority. A later attempt is allowed only if the prior outcome
is definitively known to be pre-COMMIT, the approval remains valid and
unexpired, and the globally unique `approval_id` still has no durable claim.
Such a later attempt re-enters full Stage A validation and is not an automatic
transaction retry.

Once `DURABLY_CLAIMED` is durably established, approval authority is permanently
consumed regardless of every later rollback, crash, timeout, disconnect,
failure, terminalization failure, or reconciliation failure. Ambiguous Stage A
COMMIT acknowledgement never proves absence of the claim; Stage B is forbidden.
It permits GET-only reconciliation with exact stable identifiers and no POST
retry while the outcome remains ambiguous. There is no claim stealing, lease,
expiry recovery, automatic claim recovery, delete, mutation retry, or approval
restoration. A
stranded `DURABLY_CLAIMED` claim remains consumed forever. Later transition to
`FAILED_CONSUMED`, `UNCERTAIN_CONSUMED`, or `COMMITTED` records outcome but is
not required to prevent reuse.

### 4.3 Stage B: lifecycle transaction

Before starting, require an exactly acknowledged or read-only reconciled Stage
A claim. Then, in one `SERIALIZABLE` transaction:

1. Lock and re-read the exact claim, evaluation, relevant host rows, operation
   uniqueness key, latest transitions, checkpoint-publication head, and all
   hardware-index rows needed for complete historical lookup.
2. Require claim state `DURABLY_CLAIMED` and exact claim/evaluation/operation/
   type/digest bindings. Re-derive and revalidate the exact `TransitionIntent`
   and its claimed `expected_transition_intent_digest` before any mutation.
   GENESIS, RECOVERY, and
   MIGRATION require unexpired fresh MDA bound to their challenge. DECOMMISSION
   requires no MDA but requires the exact current evaluation, target record,
   and approval.
3. For GENESIS, require complete verified immutable-history coverage and no
   historical hardware binding in either PostgreSQL or immutable history, then
   Witness-assign a new host ID and enrollment generation 1. For RECOVERY,
   preserve host ID and enrollment generation. For DECOMMISSION, make the host
   terminal. For MIGRATION, atomically decommission the predecessor and assign
   a new successor host ID with predecessor lineage.
4. Preserve nondecreasing highest release and bootstrap trust-source versions.
   Advance record generation; construct append-only transition rows and their
   chained digests.
5. Insert the exact immutable checkpoint publication intent containing the
   future stored object, computed object digest, previous checkpoint digest,
   sequence/generation, object key, and database transaction identity. The
   current chain head is not advanced until the exact stored object exists;
   publication reconciliation records its opaque immutable version ID when
   established. Insert lifecycle result and audit rows.
6. Update the claim to `COMMITTED` and commit all relational changes exactly
   once. No partial host/migration/transition/audit/operation result is valid.

The independent object publication cannot be transactionally atomic with
PostgreSQL. Therefore `COMMITTED` database state alone is not externally
reported as proven lifecycle success. The publication protocol must durably
establish the exact checkpoint and then reconcile it to the publication intent.
Until database and immutable object are exact matches, the externally visible
result is `UNCERTAIN_CONSUMED`; it grants no completion or retry authority.

Historical hardware lookup uses the append-only
`continuity_hardware_bindings`, immutable history checkpoints, and every
still-required HMAC key version. A missing historical key version, disabled or
lost required key, duplicate match, multiple-host match, ambiguous binding, or
incomplete key-version coverage yields `UNCERTAIN` and cannot establish
`COMPLETE_ABSENT` or `GENESIS_ELIGIBLE`. This document defines no reindex
mutation protocol.

A definitive pre-commit Stage B failure may be recorded in a separate bounded
transaction as `FAILED_CONSUMED`; ambiguity may be recorded as
`UNCERTAIN_CONSUMED`. Failure to record either leaves `DURABLY_CLAIMED`, already
permanently consumed. Stage B rollback never restores approval authority and
never authorizes retry.

### 4.4 Ambiguous COMMIT or delivery

If Stage A COMMIT, Stage B COMMIT, checkpoint publication, connection state, or
HTTP delivery is ambiguous, issue no mutation request. Reconcile using only
GET by the exact claim/operation/checkpoint IDs. Success requires the exact
stored operation and exact checkpoint with matching evaluation, type, claim,
hosts, transitions, database transaction identity, sequence, previous and
resulting digests, and object digest. Missing, non-exact, conflicting, malformed,
or unverifiable facts remain `UNAVAILABLE` or `UNCERTAIN`. Reconciliation cannot
complete an operation, steal/recover a claim, compensate, retry, or restore an
approval.

## 5. Immutable-history adapter contract

The repository defines an `ImmutableHistoryPort` backed architecturally by S3
Object Lock Compliance. No AWS SDK, API call, bucket, account, region, object
key, retention period, credentials, or resource is implemented here. Methods
are purpose-specific: `publish_checkpoint(intent) -> publication_result`,
`get_checkpoint(checkpoint_id, immutable_version_id|null) -> verified_checkpoint`, and
`prove_coverage(query) -> coverage_result`. There is no overwrite, update,
delete, retention-shortening, generic object, or list-as-authority method.
`immutable_version_id` is an opaque, nonempty adapter/publication-result value;
the future S3 adapter maps it exactly to S3 `VersionId`. Publication results
and persisted publication reconciliation facts bind `checkpoint_id`, object
key, `immutable_version_id` when established, `object_digest`, sequence,
`previous_checkpoint_digest`, operation ID, and database transaction identity.

Historical verification uses exact immutable versions or verified
version-aware history. A current object-key view is never historical authority.
A delete marker, current-key 404, missing current version, or inability to
enumerate and verify every required historical version is `UNAVAILABLE` or
`UNCERTAIN`, never `COMPLETE_ABSENT` or `GENESIS_ELIGIBLE`. A plain current-key
GET can neither prove history absence nor authorize GENESIS.

```text
IMMUTABLE_HISTORY_LOOKUP_VERSION_AWARE=YES
DELETE_MARKER_MAY_PROVE_HISTORY_ABSENCE=NO
DELETE_MARKER_MAY_PROVE_GENESIS=NO
LATEST_KEY_404_MAY_PROVE_HISTORY_ABSENCE=NO
LATEST_KEY_404_MAY_PROVE_GENESIS=NO
```

### 5.1 Checkpoint canonical objects

Exactly three non-circular objects define a checkpoint.

In the three schemas below, angle-bracketed values are normative type tokens,
not optional prose: `UUIDv7`, `timestamp`, `digest`, and `base64url Ed25519`
have the exact encodings fixed in section 3.1; `positive integer` is a JSON
integer from 1 through 9,007,199,254,740,991; `nonnegative integer` is a JSON
integer from 0 through 9,007,199,254,740,991; `nonempty opaque string` and
`nonempty version string` are JSON strings of at least one Unicode scalar
value; `null` is the JSON null literal. Literal strings, booleans, arrays, and
objects shown are their exact JSON types. No implicit coercion is permitted.

`CheckpointPayload` has exactly this complete version 1 schema:

```json
{
  "schema_version": "1",
  "domain": "CONTINUITY_CHECKPOINT_PAYLOAD",
  "checkpoint_id": "<UUIDv7>",
  "sequence": "<positive integer>",
  "previous_checkpoint_digest": "<digest or null only for sequence 1>",
  "database_transaction_id": "<nonempty opaque string>",
  "operation_id": "<UUIDv7>",
  "evaluation_id": "<UUIDv7>",

  ],

    {
      "continuity_host_id": "<UUIDv7>",
      "hardware_binding_index": "<base64url HMAC-SHA-256>",

    }

    {
      "transition_id": "<UUIDv7>",
      "continuity_host_id": "<UUIDv7>",

      "previous_transition_digest": "<digest or null>",

```

All listed fields are required, including nullable fields, and unknown or
additional fields are rejected at every object level. Arrays are ordered.
`affected_host_results`, `transitions`, and `version_maxima` contain one TARGET
entry for GENESIS, RECOVERY, or DECOMMISSION. For MIGRATION they contain exactly
two entries in PREDECESSOR then SUCCESSOR order; the successor result names the
predecessor and thereby freezes lineage. `hardware_bindings` contains the
ordered immutable-history binding facts relevant to the operation: exactly one
newly validated TARGET entry for GENESIS and RECOVERY, no entries for
DECOMMISSION, and exactly one newly validated SUCCESSOR entry for MIGRATION.
Historical predecessor bindings remain covered by `historical_coverage` and
prior immutable checkpoints and are not duplicated as facts created by the
current operation. Each required historical HMAC key is identified by the
ordered pair of key ID and key version; version alone is never treated as
globally identifying. Version maxima must be nondecreasing and each maxima
entry must exactly match its affected-host result.

`historical_coverage` contains historical facts only. Its through-sequence and
prior-chain-head digest cover at most the checkpoint immediately preceding
this payload; neither may describe or derive from the current checkpoint. The
payload contains no `application_payload_digest`, `signature`,
`canonical_bytes_digest`, `object_digest`, current object digest, current chain
head derived from this checkpoint's object digest, or signing-envelope-only
metadata.

```text
application_payload_digest = SHA-256(RFC8785_JCS(CheckpointPayload))
```

`WitnessCheckpointSigningEnvelope` has exactly this complete version 1 schema:

```json
{
  "schema_version": "1",
  "domain": "WITNESS_PROTOCOL_EVIDENCE",
  "evidence_type": "IMMUTABLE_CONTINUITY_CHECKPOINT",
  "checkpoint_id": "<UUIDv7>",
  "operation_id": "<UUIDv7>",
  "evaluation_id": "<UUIDv7>",
  "claim_id": "<UUIDv7>",
  "operation_type": "GENESIS_ENROLLMENT|RECOVERY|DECOMMISSION|MIGRATION",
  "continuity_host_ids": ["<all relevant UUIDv7 host bindings in transition order>"],
  "payload_schema_version": "1",
  "application_payload_digest": "<digest>",

  "witness_key_id": "<opaque id>",
  "witness_key_version": "<opaque version>",
  "signature": "<base64url Ed25519>"

```

Every field is required. Unknown or additional fields are rejected. The
ordered `continuity_host_ids` value exactly matches the payload's ordered
affected-host binding: TARGET for single-transition operations and PREDECESSOR
then SUCCESSOR for MIGRATION. It therefore has exactly one element for
GENESIS, RECOVERY, or DECOMMISSION and exactly two elements for MIGRATION. The
envelope contains no other metadata.

The signature uses the frozen AWS KMS RAW Ed25519 contract:

```text
signature = Ed25519(
  RFC8785_JCS(WitnessCheckpointSigningEnvelope excluding only signature)
)
SigningAlgorithm=ED25519_SHA_512
MessageType=RAW
CANONICAL_SIGNED_ENVELOPE_MAX_BYTES=4096
```

The byte limit applies to the exact RFC 8785 JCS byte sequence submitted for
signing—that is, the complete envelope excluding only `signature`—and is
checked before the AWS KMS adapter is invoked.

`StoredCheckpoint` is exactly:

```json
{
  "schema_version": "1",
  "payload": <exact CheckpointPayload object>,
  "signed_evidence": <exact WitnessCheckpointSigningEnvelope object>
}
```

Unknown or additional fields are rejected at the top level and within both
exact nested objects.

```text
object_digest = SHA-256(RFC8785_JCS(StoredCheckpoint))
```

`object_digest` is adapter/publication metadata and is never contained inside the
`StoredCheckpoint` being hashed. No digest contains itself directly or
transitively. No `CheckpointPayload` field directly or transitively depends on
`application_payload_digest`, `signature`, or `object_digest`. The current
immutable chain head becomes this `object_digest` only after the stored object
exists and publication has succeeded; it is never written back into that
object. Object keys contain only opaque checkpoint/operation IDs, never
hardware facts. Sequence is globally strictly increasing.

### 5.2 Coverage proof and reconciliation

A `coverage_proof` is a signed, versioned object binding the queried HMAC index
and key version set, inclusive first/last checkpoint sequences, chain-head
object digest, all required predecessor links, query time, retention-through
time, and result `COMPLETE_PRESENT|COMPLETE_ABSENT|INCOMPLETE|CONFLICTING|UNVERIFIABLE`.
`COMPLETE_ABSENT` is usable for GENESIS only when all active/historical HMAC key
versions were searched, every checkpoint from the trust root through the head
is verified, retention covers the full continuity-authority lifetime, and
PostgreSQL agrees. Listing an empty prefix is never a coverage proof.

Reconciliation compares the immutable object against its PostgreSQL publication
intent and transition chain, including exact `checkpoint_id`, object key,
`immutable_version_id` when established, `object_digest`, sequence,
`previous_checkpoint_digest`, operation ID, and database transaction identity.
Exact immutable-version re-observation is idempotent. A
different object for an ID/sequence, broken predecessor link, duplicate
sequence, digest/signature mismatch, database/object mismatch, missing object,
retention expiry, unverifiable key, or incomplete key-version search is closed
and never overwritten or repaired automatically. PostgreSQL rollback does not
establish historical absence. Missing, conflicting, expired, or unverifiable
immutable history cannot make hardware `GENESIS_ELIGIBLE`.
A delete marker, current-key 404, absent current version, plain current-key GET,
or unverified version enumeration never changes that closed result.

## 6. Cryptographic adapter interfaces

All adapters accept immutable typed values and return data or a closed error;
they expose no generic KMS operation, caller-selected algorithm, caller-selected
key, raw AWS response, credential, automatic retry, or fallback key. Inputs are
validated before adapter invocation. JCS encoding rejects floats and duplicate
keys. Binary encoding is strict unpadded base64url. Every canonical signed
object includes schema version and exact domain and is at most 4096 bytes.

### 6.1 `WitnessSigner`


`object_digest` over that complete stored object. No caller-selected field,
algorithm, key, or alternate serialization is permitted.

## 8. Closed classifications and proceed matrix

| Classification | Exact meaning | May proceed |
| --- | --- | --- |
| `GENESIS_ELIGIBLE` | Fresh valid hardware evidence plus complete verified immutable-history coverage proves no prior binding | Only to Stage A for exact `GENESIS_ENROLLMENT`; never directly to mutation or Production |
| `CONTINUITY_VALID` | Fresh valid evidence exactly matches an active record, or the approval-only DECOMMISSION evaluation exactly identifies its current record | Only to Stage A for the exact applicable lifecycle operation |
| `RECOVERY_REQUIRED` | Hardware matches an existing non-terminal identity but local continuity is absent/stale/destroyed/reinstalled, or recovery ceremony is required | Only to Stage A for exact `RECOVERY` with fresh evidence |
| `DECOMMISSIONED` | Historical identity is terminal | Read-only evidence only; no recovery, GENESIS, reenrollment, migration from it, or mutation |
| `UNAVAILABLE` | A required dependency/evidence/history/key is definitely unavailable | Stop |
| `MALFORMED` | Schema, encoding, canonicalization, attestation, signature structure, or required field is invalid | Stop |
| `UNCERTAIN` | Exact identity, key, commit, checkpoint, coverage, conflict resolution, or outcome cannot be proven | Stop; read-only exact reconciliation only where applicable |

No classification is authorization. Proceed means only that AIControlCenter may
coordinate the next explicitly defined lifecycle precondition. Missing local or
database state, unavailable/malformed/ambiguous evidence, missing/conflicting/
expired/unverifiable history, crypto failure, unknown or ambiguous signing/HMAC
key version, stale MDA, or multiple hardware matches can never become
`GENESIS_ELIGIBLE`. Failure never creates automatic retry, approval recovery,
release/install authority, SEC-02 bootstrap authority, or Production authority.

## 9. Test strategy and fakes

Tests are repository-local and deterministic. They use no Production, network,
AWS, Docker, Colima, MDM vendor, real credential, real key, or canonical
regression.

Fakes expose the same purpose-specific contracts:

- `FakeWitnessStore` models constraints, row locks, serializable transactions,
  acknowledged/ambiguous COMMIT, rollback, immutable rows, and an append-only
  audit log. It has no generic SQL escape hatch in application tests.
- `FakeImmutableHistory` models append-only Object Lock behavior, checkpoint
  chains, exact object digest, full/incomplete coverage, missing/conflicting/
  expired objects, database rollback disagreement, and ambiguous publication.
- `FakeWitnessSigner` deterministically signs only the exact Witness domain,
  rejects over-4096-byte/noncanonical input, and supports explicit key-version
  validity/ambiguity fixtures without real private keys.
- `FakeLifecycleApprovalVerifier` validates exact purpose and bindings and can
  return invalid, expired, replayed, wrong-purpose, and ambiguous-key cases; it
  cannot claim approvals.
- `FakeHardwareBindingIndexer` produces deterministic purpose/version-separated
  test indexes and models missing/ambiguous historical key versions without
  logging raw identifiers.
- `FakeDeviceInformationMda` returns valid exact-nonce evidence or explicit
  stale-cache, rate-limit, invalid-chain, nonce-mismatch, missing-identifier,
  malformed, replay, unavailable, and uncertain results.

Focused test cases must prove:

| Scenario | Required assertion |
| --- | --- |
| Normal GENESIS | Fresh exact MDA + complete immutable absence + exact approval; Stage A consumes once; Stage B assigns host/generation 1 and exact checkpoint |
| Previously enrolled hardware | Historical PostgreSQL or checkpoint match denies GENESIS regardless of local state |
| Reset/reinstall | Same hardware yields existing identity or `RECOVERY_REQUIRED`, never GENESIS |
| Recovery | Fresh evidence and exact approval preserve host/enrollment generation and nondecreasing maxima |
| Migration | Fresh successor evidence; new host ID; predecessor terminal; lineage/maxima/transitions/checkpoint atomic |
| Decommission without MDA | Exact evaluation/record/approval succeeds without calling MDA; terminal result |
| PostgreSQL rollback | Approval remains consumed after Stage B rollback; database absence cannot defeat immutable history |
| Missing immutable checkpoint | `UNAVAILABLE`/`UNCERTAIN`; never GENESIS or proven success |
| Conflicting checkpoint | Database/object or chain conflict stops and permits read-only reconciliation only |
| HMAC key ambiguity | Missing/multiple/ambiguous key version yields `UNCERTAIN`, never absence |
| Replayed challenge | Second binding/use is rejected and creates no evaluation authority |
| Replayed approval | Second claim/operation is rejected; original remains permanently consumed |
| Stranded `DURABLY_CLAIMED` | No stealing, recovery, expiry reuse, terminalization dependency, or Stage B retry |
| Ambiguous COMMIT acknowledgement | No POST retry; GET exact reconciliation only; non-exact evidence stays uncertain |

Additional contract tests validate every request/response schema, unknown-field
rejection, UUID/timestamp rules, no floats, strict unpadded base64url, RFC 8785
JCS vectors, 4096-byte signed limit, payload-digest alteration, key/domain
separation, forbidden authority fields, signed response validation, bounded GET
retry, non-retry of POST, audit redaction, immutable append behavior, transition
digest chaining, and nondecreasing maxima.

## 10. Implementation sequencing boundary

This definition permits a future repository implementation of domain types,
schema validators, ports, adapters without live calls, transaction repositories,
and fakes/tests. It does not select concrete key custody implementation details
(accounts, policies, principals, provisioning, rotation, revocation, compromise
recovery), an MDM vendor/transport implementation, cloud host, ingress topology,
deployment tool, retention schedule, disaster recovery, or Production
bootstrap. Those unresolved items keep implementation readiness closed.
